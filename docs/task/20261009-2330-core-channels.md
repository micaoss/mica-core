# 20261009-2330-core-channels Core sets on channels: the device selects, composes and rolls back core components on its own

- **status**: done
- **priority**: P1
- **owner**: mica-core
- **createdAt**: 2026-10-09 23:30
- **requestedBy**: mica-build, for the user's decision `mica:docs/decisions/2026-10-09-core-channels.md`. Design:
  `mica-build:docs/plan/20261009-2322-shared-core-releases.md`.

## Description

**Why.** Core components (`micad`, `mica-apid-ui`) are the same bytes on every product of an architecture
(`micad` arm64 `7d13629d72…` on five arm64 products, amd64 `886e1ea659…` on both amd64 boards, `mica-apid-ui`
`a7069935ec…` everywhere). Yet a deployment names its cores, so every core change is a new signed deployment
and a new release per product: about 1.2 GB of assets for about 10 MB of new bytes. The user chose to release
core components once per channel and let the device choose the channel.

**What mica-core owns, in order.**

1. **Wire forms and vectors** (`docs/mica-core.md` 6.2, the component contracts). mica-build and mica-res copy
   the vectors.
   - **`mica/core-set/v1`**, signed with the release key: `channel` (`general` or `[a-z0-9][a-z0-9-]*`), `arch`,
     `generation` (monotonic per channel and arch), `version`, and `components` (the `mica/core/v1` records of
     the channel, one per package, sorted).
   - **`mica/deployment/v2`**: product, board, generation, kernel and root, without `core`. `mica/deployment/v1`
     stays readable, and its `core` becomes the device's first core set.
   - **Catalog `mica/catalog/v2` `cores`**: lines `{channel, arch, latest: {id, generation, path}}`, additive.
     `path` names `mica/core-release/v1`: the core set (path, sha256, bytes) and its objects (sha256, bytes,
     path), with every URL `baseUrl + path` as for releases.
   - **The selection rule, as a vector**: given a core set, a product's features and a root's
     `interfaceLevel`, the components chosen, or the refusal. mica-build verifies every core set against every
     product with the same vector before it publishes.
2. **Device behaviour**:
   - **Selection**: from the installed core set, the components whose `features` `product.conf` names. Each runs
     on the deployment's root level, with every `needs` met inside the selection.
   - **The loader is unchanged; the runkit chooses the core set.** Boot records, loader entries and the FIT
     loader (`mica-build:common/uboot`) keep naming deployments only.
     - The runkit keeps a core set state on SYSTEM: `current`, and at most one `pending` with its attempts left.
     - It boots `pending` while attempts remain, decrementing them first. micad commits it to `current` once the
       boot is healthy. A boot that never gets there, a watchdog reset included, spends an attempt, and an
       exhausted `pending` is dropped.
     - The runkit authenticates the set, selects, and on a refused selection falls back to `current` before
       mapping anything.
   - **Two transactions, never pending together**: a core update stages a `pending` set; a system update stages a
     deployment and is rolled back by the loader as today.
   - **A root level change**: if a system update's root level is one the current core set cannot run on, take the
     newest set of the channel that can. Otherwise wait and report; never boot a pair known to be refused.
   - **Channel**: `update.coreChannel` in `mica/meta/v1` (default `general`), overridden by `coreChannel` in
     `/mica/config/updates.json`.
     - Within a channel, a lower generation is refused.
     - A channel switch is an operator action and may land on a lower generation of the other channel.
   - **Policies**: `off`, `check` and `auto`, maintenance windows and `rebootPolicy` apply to a core line as to
     the product line. Under `auto`, a core update and a system update in one window are installed one after the
     other, each with its own reboot gate.
   - **Status**: micad reports the installed core set, its channel and generation, and the core line's latest.
3. **A release** of the producers carrying the above, after the vectors.
