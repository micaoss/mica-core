## Description

Device testing found no way to configure MQTT: the console offered the
`mqtt.enabled` switch and a disabled prototype form, and the API had no route
that could write the rest. `PUT /api/v1/settings/{path}` takes seven dot-paths
and `mqtt.listen.address` is not one of them.

`GET/PUT /api/v1/mqtt` closes that, as a resource route rather than three more
entries on the scalar allowlist. The listener is **one decision**: an address
and a port that have to take effect together. Three scalar writes would restart
the broker three times and leave it bound to an address nobody asked for in
between.

- `GET` answers `{ configured, observed }`, not a merge of the two. A listener
  that was configured and a listener the broker is bound to differ for as long
  as the reconcile takes, and after a failed one they differ until someone
  looks. The observed half is micad's document verbatim, `available: false`
  when the reconciler has published nothing.
- `PUT` replaces the subtree and answers the apply task's id. It refuses a bind
  address that is not an IP literal and a port of 0 -- the settings tree takes
  the address as text and the broker is what finds out, which on a read-only
  root is a unit that will not start and a console that reported success.
- `mqtt.enabled` stays on the scalar allowlist: the service card's switch is a
  single-scalar write and the listener form carries `enabled` through
  unchanged, so editing a listener cannot start or stop the broker.

The console's MQTT service page gains the listener form and an observed panel
(both units, the bound listener, the rendered configuration path), and the open
listener warning is back: bound off loopback, authentication off, broker
running.

Acceptance: the route round-trips, a partial document and a bad listener are
422 with nothing written, the committed OpenAPI matches the binary, and both
suites are green.
