## Description

Device testing asked to update from an uploaded image. `mica-deploy import`
has taken an offline `MICAUPD1` archive since the partial-import work, but
nothing reached it: micad drove `check`, `fetch` and `install` and had no
member for `import`, and apid had no route.

## What changed

- `UpdateLifecycle::import_now` and `request_import` stage an archive the way
  a fetch stages a download -- the same workspace probe, the same busy slot, the
  same `--max-bytes` bound, the same `parse_fetch` on the way out, because
  `import` prints what `fetch` prints. **Not gated on the network policy**: a
  metered link, an absent source and a mode of `off` all refuse a fetch and
  none of them has anything to say about a file an operator carried here.
- `ImportUpdate(path)` on the bus, bounded to `/mica/updates/uploads`. The
  method takes a path because an archive is measured in hundreds of megabytes
  and the bus is not how those travel; bounding it is what keeps the member
  from being a way to hand `mica-deploy` an arbitrary file. The upload is
  removed once the import settles, either way.
- `POST /api/v1/update/import` streams the body into that directory under a
  name apid draws, refuses anything that does not begin with `MICAUPD1` after
  eight bytes rather than after a gigabyte, bounds the upload at 2 GiB, and
  removes the file if micad refuses the import. Answers **202**: verifying the
  objects is not a request's worth of time, and the outcome is in the update
  state the console already polls.
- The console's manual update section gains the picker, through the existing
  `FilePicker` -- the UI policy gate refuses a raw file input, correctly.
