# 20260919-1030-board-rename The device side follows the board rename

- **status**: in_progress
- **priority**: P0
- **owner**: vtv87o8e/mica-core
- **createdAt**: 2026-09-19 10:30

## Description

The boards were renamed on 2026-09-16 (`x64` to `uefi-x64`, `virt-arm64` to
`uefi-arm64`; `cx3576` and `s905x5m` unchanged) and mica-core did not follow, so
every board match in `mica-deploy` still named the retired spellings. The
assembly writes the new name into the signed deployment envelope and the signed
boot policy: the envelope of the published
`mica-uefi-x64-dev-20260919-2103.micaupd` decodes to `"board":"uefi-x64"`
(coordinator, range-fetched from the release).

**This is not "updates break", it is "the device does not boot."**
`BootKind::for_board` is called from `mica-runkit` `init.rs:337` **as PID 1,
before systemd**, and `bin/mica-deploy.rs:219` calls it on every invocation
before any subcommand -- so `mica-deploy booted` fails, the health gate
`/usr/lib/mica/mica-health` fails with it, `mica-boot-failure.service` runs
`mica-deploy fail-boot`, that fails too, and its else branch powers the device
off.

The one piece of good news: all four sites are exhaustive matches with an
explicit error arm. There is no silent default and no wrong branch, and the
worst shape -- `uefi-arm64` falling through to an amd64 default at
`firmware.rs:46` -- does not exist, because that match ends in `bail!`. A device
refuses; it never mis-targets.

## What changed

- `boot.rs` `BootKind::for_board`, `components.rs` `Deployment::validate`,
  `firmware.rs` board-to-architecture and the EFI file name: new names only, no
  aliases, per the no-compatibility rule. The retired names are refused.
- The six test files and the three shared fixtures
  (`tests/component-contracts/`), regenerated through their generator so the
  ids and signatures follow: `deploymentId` is now
  `7091da552d8cd8359568dc7803c0e78d46626597c15f665b85c5f0c4818409cf`.
- `cases.json` gains a `boards` block: the vocabulary as data, one case per
  name with its architecture, boot format and backend, and the retired `x64`
  and `virt-arm64` listed as **refused**. `tests/contract_cases.rs`
  `board_vocabulary` drives every entry through `BootKind::for_board` and
  `parse_deployment`.

## Why the gates did not catch it

`tests/component-contracts/` is the shared contract and the assembly refuses a
divergence from the copy at the pinned commit, so the mechanism existed. The
gap was that the fixtures carried `x64` as a *sample value* rather than as a
*vocabulary*: nothing stated "these are the board names" in a form a gate
reads, so a rename on one side could not fail anything on the other. The
`boards` block closes that: both repositories verify the same list.

## ActiveForm

Following the board rename through the device side

## Dependencies

- mica-build takes these fixture bytes after it re-pins mica-core. The order is
  mica-core first: if the assembly changed its copy first, its own contract
  check would fail against the pinned mica-core.
