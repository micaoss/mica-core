# 20260920-0700-network-page The network page shows what the device has and edits it

## Description

Device testing walked the network page and found most of it read-only or
misleading:

- the interface list showed every observed link, including the loopback and a
  `veth` per running container, so finding `eth0` meant scrolling past the
  engine's plumbing;
- the whole observed panel was repeated under the list, restating the same
  interfaces a second time;
- an interface could be declared and never edited or removed -- the danger zone
  was a sentence with no button;
- a VLAN's parent and a bridge's ports were free text, so a typo became an
  entry micad refuses;
- a WireGuard tunnel was offered DHCP, a gateway and DNS, none of which a
  tunnel has;
- a tunnel's own peer block -- the thing the remote side needs -- was nowhere,
  and the public key appeared only for a moment after a rotation;
- a stored Wi-Fi network could be added and forgotten but never edited, and
  which radio the station runs on was displayed as the literal `wlan0`.

## What changed

**The console.** `visibleNetworkRows` hides the loopback and the container
engine's virtual ends while always keeping a declared entry;
`physicalInterfaces` answers what a VLAN parent and a bridge port may be, and
both are selectors now. The observed panel moved to its own tab (routes, DNS,
radios), and each interface's own observation -- addresses with their source,
the lease, link DNS, the association -- is on that interface's page, rendered
by the same component the panel uses. The interface page gained the kind-level
fields (VLAN parent and id, bridge ports, tunnel listen port) and a delete
behind a confirmation. A tunnel is offered neither DHCP nor a gateway, and its
page and the add dialog say why. The WireGuard tab prints the device's own
`[Peer]` block with a copy control, read from the public key the network
reconciler publishes into live state.

**Two new API routes**, because the console could not do this without them:

- `GET/PUT /api/v1/wifi/client` -- the station role, its radio and its switch.
  `wifi.client.interface` was on no writable path at all, so moving the station
  to another radio meant editing the document on the device. Two scalar writes
  under the hood, deliberately: a whole-subtree write would have to carry the
  network list, and that means every stored key travelling back through the API
  on every switch flip.
- `PUT /api/v1/wifi/client/networks/{ssid}` -- replace one known network.
  **`psk` absent keeps the stored key**: a read substitutes the redaction
  sentinel, so an operator changing a priority has not been shown the key, and
  treating absence as "open network" would silently drop a working credential.
  The sentinel written back is refused, as it is on the add route, and a body
  that renames the entry is refused rather than guessed at.

Not in this task: static routes and a DHCP server, which need settings-schema
changes (20260920-0701, 20260920-0702), and the AP's connected clients, which
needs an observation micad does not make (20260920-0703).
