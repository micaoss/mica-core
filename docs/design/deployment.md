# Deployments and early boot: mica-deploy, mica-runkit, lifecycle-sys

A Mica OS device runs a signed, read-only root. Updating it means installing a
new **signed file deployment** beside the running one, booting it on trial, and
confirming or rolling it back. `crates/mica-deploy` implements that on the
device; `mica-runkit` is the early-boot and shutdown executable that enforces it
before and after systemd; `crates/lifecycle-sys` is the small `unsafe` layer of
device operations both need.

## 1. Storage

| Location | Holds |
| --- | --- |
| SYSTEM (`/mnt/system`) | The deployments: descriptors, signatures and content-addressed component objects (kernel, root and support images). A strict two-deployment budget |
| ESP (`/boot`, UEFI) or the U-Boot environment (FIT boards) | The boot records selecting a deployment and counting trial attempts |
| DATA (`/mnt/data/meta`) | Native transaction state, catalog checkpoints, the firmware receipt |
| DATA (`/mica/updates`) | Downloads, verified descriptors and staged objects; nothing of an acquisition is written to SYSTEM |

SYSTEM and the boot partition are mounted read-only and remounted writable only
inside an operation, under the deployment transaction lock.

## 2. Signed metadata

Every piece of metadata is a strict JSON document verified with Ed25519 against
public keys embedded in the signed kernel image or the device policy
(`components.rs`, `catalog.rs`, `firmware.rs`). Unknown fields are refused.

| Schema | What it signs |
| --- | --- |
| `mica/deployment/v2` | A deployment: its identity, its product, the components and the data policy |
| `mica/kernel/v1`, `mica/rootfs/v2` | The kernel and root/support components and their verity parameters; neither carries a version, so a component's id changes only with its content |
| `mica/update-envelope/v1` | The envelope a published update travels in |
| `mica/firmware/v1` | Firmware maintenance; kept apart, no deployment can carry firmware |

| `mica/catalog/v2` | The online catalog: releases and a channel head per board, product and channel |

A deployment names its `product`, the `products/<name>` it was built as
(`x64-dev`, `x64-minimal`; the profile is part of the product). The device's
product is the single unquoted `PRODUCT=<name>` line of
`/usr/lib/mica/product.conf` in its running, verity-authenticated root;
`check`, `fetch`, `import` and `install` refuse a deployment naming another
product, and the catalog selects only the device's board, product and channel.

Offline component archives start with the eight-byte magic `MICAUPD1`, followed
by the signed descriptor, an object count and the objects. One product release
ships its descriptor as up to three archives: `.micaupd` with every object,
`.root.micaupd` with the root objects (when the kernel is unchanged) and
`.kernel.micaupd` with the kernel objects (when the root is unchanged). An
archive may carry any subset of the descriptor's objects, each named by it,
listed once and checked by size and digest; after the stream every object it did
not carry must already be installed or verified, or the import is refused
("deployment objects are incomplete"). Only these exact schema ids and this
magic are accepted. The component contract fixtures in
`crates/mica-deploy/tests/component-contracts/` are shared with the assembly
that produces these archives, which keeps a byte copy of them. They are
generated by `cargo run -p mica-deploy --example component-contract-fixtures --
crates/mica-deploy/tests/component-contracts` from the unsigned inputs in
`cases.json` and `firmware.json`, signed with TEST-ONLY keys that no image or
update server trusts, and `tests/contract_fixtures.rs` holds the committed files
to that output.

## 3. mica-deploy

`/usr/bin/mica-deploy <command>`. It prints JSON on stdout, exits non-zero on
failure, and bounds every read (`--max-bytes`, 512 MiB by default). micad
drives it (`crates/micad/src/deployment.rs`) with its own timeouts.

| Command | Does |
| --- | --- |
| `status` | The boot receipt, the effective state and every deployment's description |
| `check --source <url> --channel <c>` | Fetch the signed catalog, check freshness, select the exact components for this device |
| `fetch --source <url> --channel <c>` | Download the selected deployment's objects into DATA, streaming and verifying |
| `import <archive>` | Take a deployment from an offline `MICAUPD1` archive, full or partial |
| `install <descriptor> --objects <dir>` | Install under the lock: verify every object, check capacity and generation, publish into SYSTEM, write the trial boot record |
| `booted` | Print the running deployment's id, only if its content was authenticated |
| `confirm` | Make the running trial deployment the confirmed one |
| `reject <id>` | Reject a deployment while a usable fallback remains |
| `rollback` | Reject the confirmed running deployment and select its retained fallback |
| `fail-boot` | Retire the running deployment after a failed trial boot |
| `probe`, `discard` | Report or remove the acquisition workspace under `/mica/updates` |
| `gc` | Remove objects on SYSTEM that no retained deployment references |
| `firmware-readback [manifest] [--record]` | Authenticate a firmware manifest for this board, verify the firmware by reading it back, optionally record the receipt |

Installation is a durable file transaction: every step is written atomically
and synced, and the fault suite (`scripts/gate/file-ab-faults/`) interrupts the
real transaction code before and after each observed IO operation to prove
recovery.

### What "confirmed" means, and what it deliberately does not

`confirm` is not a statement that the product works. It removes the trial
counter, promotes the slot to `current`, and makes returning to the fallback an
explicit operator action. So the question it answers is narrower and sharper:
**can this slot still be reached and still be changed** -- because a slot that
can be updated can be repaired without the fallback, and one that cannot must be
handed back while the trial counter still exists.

The boot health gate that calls it (`mica-system-base:/usr/lib/mica/mica-health`,
required set in `/etc/mica/health.conf`) checks exactly that: the boot
transaction finished (`boot-settled`), micad answers on the system bus, and apid
answers `https://127.0.0.1/healthz`. Failed units are **reported** to micad and
never fatal, and `systemctl is-system-running = degraded` passes.

That boundary is deliberate in both directions:

- Requiring `running` would refuse to confirm a boot where one unrelated unit
  failed, and hand the device to the fallback for a cosmetic fault. Rollback is
  a blunt instrument -- it discards the whole deployment -- so it must not be
  triggered by anything the next update could fix.
- `boot-settled` treats `starting` with **no other running jobs** as settled,
  because the gate is itself a job of the boot transaction: while it runs,
  `is-system-running` cannot be anything else. A capture taken during the gate
  therefore shows `starting` with `systemctl --failed` empty, and that is the
  gate working, not a slot confirmed early.

So "good" means recoverable, not healthy. A unit that fails after the gate has
run is a normal fault to be fixed by configuration or by the next deployment;
it is not a reason to lose the deployment that is running.

### 3.1 Policy on top: micad

micad adds what an operator decides (`crates/micad/src/update_*.rs`): the
automatic check cadence, the maintenance window, the safe-to-reboot gate and
its bounded override, the failed-ID list and generation floor that stop a
rejected release from reinstalling. apid exposes all of it under
`/api/v1/update`.

## 4. mica-runkit

One static executable (package `mica-lifecycle`,
`/usr/lib/mica/lifecycle/mica-runkit`). The assembly places it into the signed
kernel image; it is never installed into a root. The name it is invoked by is
the only selector.

### 4.1 `init`: the authenticated initramfs PID 1

1. Mount `/dev`, `/proc`, `/sys` and a bounded `/run`; require that dm-verity
   enforces signatures.
2. Arm the boot watchdog before touching deployment storage.
3. Read the device policy (`/etc/mica/boot.json` in the signed initramfs:
   identity, public keys, SYSTEM and DATA partition UUIDs) and check the running
   kernel release against it.
4. Select the deployment the boot record names, authenticate its descriptor,
   and open the root and support images as signed dm-verity mappings.
5. Establish persistent identity on DATA, bind kernel modules and firmware from
   the read-only support image, validate the new root, and hand over to systemd.

No network and no shell are available at this stage, and no policy can enable
them.

### 4.2 `shutdown`: the exit ramdisk PID 1

systemd hands over to a memory-only retained exit ramdisk. `shutdown` releases
loop devices and device-mapper mappings in dependency order, so each backing
filesystem is unmounted after everything on top of it, with one bounded policy
shared by a clean shutdown and a partial-startup refusal
(`crates/mica-deploy/src/boot/shutdown.rs`).

## 5. lifecycle-sys

`crates/lifecycle-sys` wraps the Linux device operations early boot and
shutdown need — watchdog support, timeout and keepalive; loop device status and
clearing; device-mapper status, table and removal — as typed, bounded functions.
It is the only crate allowed `unsafe`, by a dated decision, and the boot/shutdown
gate compiles its UAPI translation unit for x86-64 and aarch64
(`scripts/gate/boot-shutdown-test.sh`).
