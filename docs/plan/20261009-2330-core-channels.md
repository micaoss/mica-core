# Plan: core sets on channels

Task: `docs/task/20261009-2330-core-channels.md`. Status: **approved** (the user, 2026-10-09).
Decision: `mica:docs/decisions/2026-10-09-core-channels.md`. Producer side:
`mica-build:docs/plan/20261009-2322-shared-core-releases.md`.

## What exists today (the parts this touches)

- `mica/deployment/v1` names `core`, the `mica/core/v1` records (`components.rs` `Deployment`,
  `CoreComponent`). Reading a deployment checks each core against the root's `interfaceLevel` and
  against the others' `needs` (`check_composition`).
- The runkit maps each core component as verity and overlays `/usr` and `/etc`
  (`bin/mica-runkit/init/mounts.rs` `compose_core`).
- Boot records, loader entries, attempts and rollback are per deployment (`deployments.rs`,
  `deployments/lifecycle.rs` `confirm`). None of that changes.
- The catalog reader ignores fields it does not know, so a `cores` list in `mica/catalog/v2` strands no
  device already released.
- `/usr/lib/mica/product.conf` in the root carries `FEATURES`, the words mica-build selects cores by.

## Decisions

1. **Two core sets at most (the user, 2026-10-09).** The device keeps the set it runs and, while one is
   being tried, the set it is updating to. Once the new set is healthy the old one is released; a set
   that fails is dropped. There is no third, and no way back to a set that was replaced by a healthy one.
2. **The loader is untouched.** The runkit chooses the core set from a state file on SYSTEM:
   `current`, and at most one `pending` with its attempts left. The loader keeps choosing a deployment.
3. **Never both pending.** A core update is refused while a deployment is on trial, and a system update
   while a core set is pending, so a failed boot always has one cause and one thing to undo.
4. **A root level change is ordered, not paired.** A system update is installed only when the current
   core set selects on the new root. If it does not, and the channel's latest set selects on both the
   running root and the new one, the device installs that core set first and the system update after
   it. Otherwise it waits and reports which set and which level disagree. The catalog offers only each
   channel's latest, so "the newest set that can" is that set or nothing.
5. **A v1 deployment's `core` is generation 0.** On the first boot of a core-capable runkit with no core
   set state, the booted v1 deployment's `core` becomes `current` as an unsigned local set of the
   device's channel at generation 0, so the first published set of any channel is newer. It is
   authenticated through the deployment that carried it.
6. **One selection rule, in one place.** `mica_deploy::core_set::select(set, features, root_level)` is
   what the runkit, mica-deploy's acquisition and the vector test call. mica-build ports it against the
   vector.

## Wire forms

All canonical JSON; the signed ones strict (unknown fields refused), the catalog ones tolerant.

**`mica/core-set/v1`**, in a `mica/update-envelope/v1` signed with the release key:

| field | rule |
|---|---|
| `schema` | `mica/core-set/v1` |
| `channel` | `general` or `[a-z0-9][a-z0-9-]{0,31}` |
| `arch` | `amd64` or `arm64` |
| `generation` | 1 to 2^53-1; monotonic per channel and arch |
| `version` | for people, at most 64 characters |
| `components` | 1 to 16 `mica/core/v1` records, sorted by `package`, one per package, each of this `arch` |

Its id is the component id of the document, as for a deployment.

**`mica/deployment/v2`**: `mica/deployment/v1` without `core`. v1 stays readable; a v1 `core` is used
only by decision 5.

**Selection** (`select`): the components with a feature in the product's `FEATURES`, sorted by package.
Refused when one does not run on the root's `interfaceLevel`, or needs a package that is not selected or
is selected at a version outside the range. An empty selection is not a refusal: a product may carry no
core.

**Catalog**, additive in `mica/catalog/v2`: `cores: [{channel, arch, latest: {id, generation, path}}]`,
one line per channel and arch. `path` names **`mica/core-release/v1`**:
`{schema, baseUrl, id, channel, arch, generation, coreSet: {path, sha256, bytes}, objects: [{sha256, bytes, path}]}`,
read and checked the way `mica/release/v1` is: the document agrees with its line, the envelope with its
digest and length, the signed set with the line's channel, arch and generation, and `objects` are
exactly what the set names.

**State on SYSTEM**, `meta/core.json`, written atomically:
`{current: <id>, pending?: {id, attemptsLeft}}`; envelopes at `core-sets/<id>.json`.

## Device behaviour

- **Runkit**: reads the state. With a `pending` that has attempts left it decrements, syncs, and tries
  it; otherwise `current`. It authenticates the envelope with the kernel's keys, selects against the
  mounted root's `product.conf` and level, and composes as today. A pending set that fails to
  authenticate or select is dropped before anything is mapped, and `current` is used. A `current` that
  fails stops the boot, as an unreadable deployment does.
- **Commit**: micad's health confirmation, the one that confirms a deployment today, promotes `pending`
  to `current` and releases the old set's objects that the new one does not name. An exhausted
  `pending` is dropped the same way.
- **mica-deploy**: `core check`, `core fetch`, `core install` beside the deployment verbs, sharing the
  object store, the byte budget and the delta transfer. Collection keeps the objects of `current`,
  `pending` and every installed deployment.
- **micad**: `update.coreChannel` in `mica/meta/v1` (default `general`), `coreChannel` in
  `/mica/config/updates.json`. Check and auto run the core line with the product line's policy, windows
  and reboot gate, one after the other. A channel switch discards the generation floor of the old
  channel; within a channel a lower generation is refused. Status: the installed set (channel,
  generation, version, id), the pending one, the line's latest, and why an update is waiting.

## Risks

- **A core set that breaks micad cannot confirm its own health.** That is the case rollback exists for:
  the attempts run out and the runkit goes back to `current`. The attempts are spent before the root is
  mounted, so a set that hangs the boot is covered by the watchdog reset.
- **No way back after a healthy commit.** A regression found later is fixed by a newer set, not by
  rollback; this is what two sets means, and it is the user's choice.
- **`product.conf` must keep naming the core-selecting features.** mica-build writes them today
  (`rootfs/build.ts`); the selection vector pins the words.

## Scope

mica-deploy (reader, acquisition, runkit), micad, micad-settings, mica-apid (status and the update
page), the component contracts, `docs/mica-core.md`. Not the loader, not the FIT loader, not the boot
records.

- **Steps 1 and 2 done (2026-10-09), not released.** `core_set.rs` (`parse`, `authenticate`,
  `select`, `device_features`), `catalog/cores.rs` (`verify_core_catalog`), `mica/deployment/v2`.
  mica-build's session had drafted the set, the selection and the tests in this tree before the plan
  was approved; they were taken over, moved out of `components.rs` and put behind the generator.
- **Vectors**: `core-set.json` (`payload`, `envelope`, `coreSetId`, `selections`), and in
  `catalog.json` the manifest's `cores` line with `coreReleaseUrl`, `coreRelease`, `coreSetUrl`,
  `coreSet`. Inputs: `cases.json` `coreSet`.
- **Fixed with mica-res (the user, 2026-10-09)**: a core release is a release of the product
  `core.<channel>`, named `core.<channel>.<stamp>` on every architecture's line; its directory holds
  `<arch>/index.json`, `<arch>/core-set.json` and `<arch>/objects/<sha256>`, with `baseUrl` the
  `<arch>/` directory. The core archive is `MICAUPD1` with the signed set as its envelope.
- **Step 3 done (2026-10-10), not released.** One change from the design above, found in the
  code: the runkit mounts SYSTEM read-only and must keep doing so, so the state is two files.
  - SYSTEM `core-sets/state.json` names `current` and at most one `pending`. Only the running
    system writes it (`mica-deploy core-install`, `confirm`); it survives a reset of DATA.
  - DATA `meta/core-trial.json` counts the pending set's boots. The runkit mounts DATA before it
    composes, spends one boot, then tries the set. A trial that is missing, another set's or spent
    means the pending set is not tried.
  - `core_state::composition` is the runkit's whole decision, tested without a boot. A pending
    set that does not authenticate or select is passed over; a boot that fails with a set on
    trial does not retire the deployment (the runkit's own failure path and `mica-deploy
    fail-boot` both check it).
  - Base's health gate is unchanged: `mica-deploy confirm` commits the set that was booted, or
    drops one whose trial is over, and releases the components nothing names
    (`deployments/core.rs`). `mica-deploy core-status` reports.
  - The runkit leaves `/run/mica/core.json` (`coreSetId`, `pending`) and `/run/mica/core-set.json`
    rather than adding fields to `boot.json`, which an older mica-deploy in the root would refuse.
  - A deployment is not installed while a core set is pending, nor when the current set does not
    select on its root, nor as `mica/deployment/v2` on a device with no set.
  - Decision 5 became simpler: a device with no state composes its `mica/deployment/v1` `core` as
    before, with no generation; its first installed set is the first of its line.
- **Step 4 done (2026-10-10), not released.** `mica-deploy core-check` and `core-fetch`
  (`acquisition/cores.rs`) share the workspace, the budget, the object store, the delta transfer
  and the manifest checkpoint with the product line. `import` reads either archive and names
  which (`kind`: `deployment` or `coreSet`). Collection of the workspace is unchanged.
